# Known limitations

## Strategy evidence

- No durable profitable alpha has been established. The current readiness artifacts say `baseline_only_no_candidate` / `no_active_candidate`.
- The retained shadow snapshot is only 66 closed trades across 32 markets and five runs. It is too small and too simulation-dependent for a performance claim.
- A small meta-fusion holdout did not beat its baseline on Brier score. Treat all learned weights and the bundled ONNX model as research artifacts.
- Historical reports were produced under specific market regimes and cannot establish future performance. Maker evaluation binds selected noncredential configuration; new model training also fingerprints the consumed base tensors and split, actual exported ONNX bytes, selected source files and arguments. These are unsigned content identities, not deterministic training, a complete source-binary identity or independent evidence. Legacy reports remain insufficient.
- The source snapshot bundles a reproducible, untrained model for runtime demonstration. It has no learned trading edge and must not be treated as a funded trading model. The earlier model with undocumented training provenance is excluded from this source package. See [MODEL_ARTIFACT.md](MODEL_ARTIFACT.md).
- The API's default `synthetic_ta` backtest uses simplified TA fusion and independently configurable fixed YES/NO purchase-price assumptions, defaulting to 0.50 each. Version 2 corrects expected-return/cost units, requires affordable entry costs and fetches through the requested completed-candle horizon. Prices are hypothetical, not reconstructed venue quotes. Non-0.50 TP/SL proxy or adaptive win-rate combinations are refused; asymmetric break-even summaries remain unavailable. Maker mode adjusts assumed costs rather than replaying the production quote/fill lifecycle. The separate bounded `decision_replay` mode compares supplied captures against current shared production decision functions, without executing the actor or evolving a portfolio; it does not authenticate captures. Neither mode validates full historical venue execution.
- New training runs reserve a chronological, market-disjoint holdout, but an already consulted historical period is not independent evidence. Internal selection metrics and legacy full-dataset Brier scores must not be presented as unseen performance.

## Operational evidence

- Shutdown/reconciliation has automated coverage for multiple positions, database-only exposure, unreadable persistence, actor drain, fill-ledger recovery and a subprocess crash/restart boundary. A multi-open shutdown observation using real market inventory remains evidence-incomplete because the latest validation window had no target markets/trades.
- Live trading with meaningful capital has not been independently validated as part of the current engineering baseline.

## Live execution boundaries

- The server exposes no arbitrary raw-transaction relay or standalone priority-fee endpoint. Those unused routes bypassed execution records and mode safeguards and were removed. The public Rust RPC utilities remain library tools, not server operations. The exchange adapter's finalized-receipt verification uses its own read-only RPC path.
- Direct maker quote/inventory state editing is not exposed over HTTP. The removed debugging routes could insert or hide in-memory quotes without venue submission/cancellation and overwrite inventory without fill evidence. Maker state remains readable; supported trading, closing and recovery actions use the execution actor and durable evidence.
- Durable maker orders, confirmed fills, cancellation races and restart recovery flow into position/fill ledgers. Maker and hybrid live profiles require `maker_live_quoting=true`, successful preflight and working receipt verification. A hybrid cross runs only through the execution actor after cancelling all resting maker orders, reconciling finalized fills, proving durable/actor reservations resolved and refreshing collateral. Direct hybrid submissions are refused. Turning real quoting off never substitutes simulated fills for real inventory. Manual market stand-down persists across restart.
- Maker admission currently requires a known zero-maker-fee schedule. Unknown or nonzero maker fees stop new quotes; receipt accounting still records actual fees if the venue charges them. This restriction needs explicit validation before extending support to fee-bearing maker markets.
- The adapter supports EOA, Polymarket Proxy, Gnosis Safe and Deposit Wallet signatures. CTF markets use V1/V2 and their normal or negative-risk exchange domains; position-ID markets are explicitly routed to V3 from market metadata. Deposit Wallets require V2/V3. Unknown versions, missing funding addresses or incomplete venue rules are refused. Signing fixtures establish wire compatibility, not wallet deployment, approvals or venue permission.
- Taker and maker execution quantities, prices and actual fees come from successful, canonical, finalized Polygon receipts associated with confirmed account trades. V1 BUY share fees reduce owned inventory; V2/V3 collateral fees are accounted separately. Current fee curves budget an order; they do not reconstruct historical fees. An explicit trusted HTTPS Polygon RPC with finalized-block support is required before funded submission. The RPC is a trust dependency, not an independent cryptographic proof.
- Taker entries and sales use FOK with durable signed order hashes saved before submission. A timeout never permits a new submission. Deliberate live partial closes are supported through the actor; manual fractions require an operation idempotency key, and automatic live partial take profit requires the separate `live_partial_take_profit=true` opt-in. A dispatched partial sale records a per-lot request generation before queueing. A lost reply, timeout or unconfirmed outcome retains that lot's automatic-exit hold; it cannot fall through to another automatic full sale, resolution mark or synthetic maker flattening. Other lots retain their exit checks. Only matching known completion or reconciliation of its specifically bound finalized live EXIT evidence may release the hold. REST and stream positions expose the hold, and the dashboard marks the pending outcome. The in-process request guard is not a new durable paper intent before queueing; persisted live EXIT reservations remain authoritative across restart. Finalized actual quantities/fees determine accounting. Two-decimal size precision and venue minimums apply to both the sale and remaining lot; unsupported dust stays visible. No automatic dust liquidation is provided.
- `pair_merge` is paper-only and requires two open, non-live, same-market complementary lots with equal positive quantities, checked at admission and again at dequeue. Both lot closures, fill evidence and dated realized P&L must commit together in one database transaction; cash and in-memory positions publish only afterward. A failure on either leg rolls back the pair. The process must also satisfy the paper-origin guard: its current recognized mode is paper, shadow or simulation, and it has no immutable boot-time live-wallet client. Held or mismatched pairs are deliberately deferred; partial merge is unsupported. The retained `maker_pair_merge_max_share_mismatch` compatibility setting does not authorize synthetic full settlement of unequal lots. This path provides no live onchain merge or redemption.
- Paper and shadow entries, simulated maker fills, full and partial paper sales, pair settlement and balance resets require both a recognized non-live runtime mode and the absence of a boot-time live-wallet client. A live mode with the shadow flag set is still refused; changing a wallet-backed process to a non-live config cannot convert its cash origin. These paths cannot create, debit or credit paper cash in that process. Legacy mixed paper lots remain unresolved there and require an isolated paper process without a live-wallet client; they are not silently credited into venue cash.
- Uncertain submissions remain reserved and uncertain exits remain `CLOSING`, survive restart and block exposure. Each pending maker or taker recovery pass uses one 20-second external-read deadline; unresolved intents survive expiry, while durable commits and completed cash publication are not cancelled by that timer. Database work can extend the total turn. Bounded periodic audits revisit settled maker and taker evidence; changed, missing or unavailable evidence creates durable uncertainty without rewriting inventory or profit. The taker audit rotates eight settled order IDs every 30 seconds, so revisit latency grows with history. Older settled rows can acquire a baseline only after current complete history/receipt verification; that does not attest earlier unseen states. Authenticated evidence exports and original-baseline rechecks are documented in [the recovery runbook](../ops/recovery-runbook.md). Rechecks retain stops and cannot waive changed evidence. Arbitrary external-wallet/legacy repair is unsupported; receipt-backed entry basis is required for resale and the narrow redemption path. Redemption checks fresh entry fill logs against durable quantities, costs and actual fees; a transaction success envelope alone is insufficient.
- Gamma resolution does not prove paid collateral. The expiry guard retains live inventory and partial-sale profit and freezes entries. Operator-requested reconciliation supports finalized standard CTF collateral-adapter redemption into pUSD only, with canonical account transfers/burns/payout, exact complete managed lots and receipt-backed entry/partial history. It signs/sends no transaction. The loop must be stopped and entries frozen; configuration and unfreezing controls are excluded during repair. Negative-risk, V2 PositionManager/Router, V3/direct-USDC.e variants, foreign mixed holdings and unverified legacy basis remain unsupported. Redemption P&L excludes native gas and external transaction costs. Automatic redemption is not implemented.
- Local HTTP/RPC contract tests, SDK signing fixtures and crash/restart tests validate these engineering contracts. No real funded trade was submitted during this validation. They do not establish continued venue compatibility, complete external-wallet reconciliation or profitable strategy behavior. See [the protocol evidence](evidence/POLYMARKET_CONTRACT_COMPATIBILITY_2026-10-10.md).

## Evaluation and data limitations

- The static 2026 macro calendar remains a reference. Optional `macro_event_auto_refresh=true` renews selected CPI, Employment Situation and regular FOMC dates from official sources with expiry, strict parsing and a bounded background worker. It covers neither every macro event nor emergency announcements. A failed refresh preserves the file and an enabled stale guard blocks entries. Both guard and refresh default off. The Fed parser was checked against its public page; BLS returned403 during this network probe, so a complete live refresh is not claimed.
- Advanced options inputs now use actual Deribit ticker delta/IV and complete open interest for a bounded1–30-day single-expiry BTC slice, with refresh/freshness and completeness gates. Skew and IV are heuristic proxies, not a full options surface or alpha proof. Unsigned open interest cannot establish signed dealer inventory/GEX; that quantity remains unavailable.
- A late-window token price by itself cannot establish independent edge. The price-only fallback holds rather than fabricating positive expected value.
- Historical reconstructed training inputs are not exact live observations. Publishing a model from them is refused; independent data and strategy evaluation remain the operator's responsibility.
- Daily realized P&L uses UTC events: validated maker execution seconds, paper sale time, recognition time of a finalized taker settlement, and finalized block time for supported external redemption. A delayed taker receipt can therefore land on a different day from execution. Maker timestamps must agree across a transaction and repeated evidence; implausible future/millisecond timestamps are refused. Undated legacy partial histories remain unavailable and block risk admission; unallocated historical losses remain separate.
- Sequential paper A/B windows can differ in external conditions even with identical non-treatment settings; they are observational evidence, not randomized causal proof.
- History cannot be deleted through HTTP because erasing closed trades also erases the basis for reconstructing cash. Use session boundaries to filter the display and preserve verified backups.

## Architecture and maintenance

- One active service owns a SQLite database inode through a kernel-held advisory lease; cooperating second instances, including symlink/hard-link aliases, are refused and crash releases ownership. This is not a distributed system or protection against an operator replacing an active database file. Use a supported local filesystem and never replace/restore a live database.
- Several venue/telemetry contracts and coordination functions retain high argument counts. Their Clippy exceptions are local and documented; global argument-count, nested-type and lock-across-await exemptions are removed. The fusion core uses named inputs and complex nested contracts use named types. Larger coordinators remain refactoring opportunities.
- The executable imports the library tree. Live sale, redemption, recurring taker audit, options and backtest helpers have focused modules. Actor regression tests are separated from production coordination; the actor and analysis coordinator still carry maintenance cost. The distribution does not include a complete architectural rewrite.
- `config.json` retains one broad typed contract and historical tuning choices. The dashboard separates everyday operating controls from a closed experimental-settings disclosure and labels paper execution assumptions as unmeasured. Operating mode, macro calendar path and starting balance are visible read-only and excluded from save payloads, including stale markup. Runtime patches containing `initial_balance` are rejected atomically, even with a sensitive-config override; they cannot publish cash outside the execution actor. Configure startup-only values before launch or use the signed, non-live balance reset API for cash origin, which is serialized with entries and exits and requires the immutable non-wallet process origin. This UI separation is not a wholesale configuration-schema rewrite.
- A local source-build installer creates a new private runtime/state directory, verified assets and safe research-only launcher without overwriting an existing installation. It uses the reviewed stopped research template, generates private dashboard credentials for each installation, supports explicit saved-key retrieval without starting the engine, and verifies installed vendor bytes. It requires reviewed prerequisites and does not install system tools or validation packages. An optional [research container recipe](../ops/container.md) keeps the real dashboard, native demonstration model and private persistent state together, with feeds/trading disabled, a non-root user and loopback host publication. It installs no container engine and is not a funded launcher; actual engine/architecture acceptance is separately scoped. There is no hosted control plane, billing, tenant isolation, native app or customer support system. 

## Remaining code-surface debt

The unwired hedging, bundling, probe, alternate market-making, model A/B, and multi-agent personality
modules have been removed from the active source tree. Those experiments are not part of the current implementation.

The obsolete dead-code suppressions have been removed and strict compiler/Clippy checks
remain enabled. Uncalled authentication and pruned-provider stubs, plus the unused
midpoint-based routing experiment and its test, were removed. Public library and
research APIs are retained; compiler reachability does not establish strategy value.

## External dependencies

- Exchange schemas, endpoints, rate limits, fees, geofencing, and terms can change.
- Live operation depends on external market-data and sentiment providers whose availability and licenses are outside this repository.
- The first uncached build obtains Rust dependencies and official ONNX Runtime bytes. Local setup supports an explicitly offline build when prerequisites, Cargo dependencies and verified runtime cache/archive are already available; it never silently falls back to a downloader in offline mode.
- The CPU model runtime is installed separately from a checksum-pinned official archive. The supplied native installer targets macOS ARM64 and Linux x64/ARM64; other platforms need a reviewed artifact and integration work. Actual Ubuntu 26.04.1 ARM64 compilation, pinned Python installation, model comparisons and installed research lifecycle passed; the successful retry reused the initially cold build target. Linux x64, Windows and other OS/architecture combinations remain unverified. See platform evidence. Models/checkpoints must be trusted local artifacts. Native parsing is not a sandbox, and exact file hashes do not prove every upstream function is correct. See [DEPENDENCY_DISCLOSURE.md](DEPENDENCY_DISCLOSURE.md).
- Python database writers require their interpreter's native SQLite to be at least 3.51.3. Installing the Python lockfile alone does not upgrade that library. Read-only reports can use older runtimes; the full gate checks the writer requirement explicitly.
- Python package pins do not replace the interpreter or its native TLS library. The full verification gate requires Python 3.11.17+ within the 3.11 series and a reviewed patched OpenSSL branch. The optional native provisioning helpers build verified releases outside the source tree; the loaded Python 3.11.17, OpenSSL 3.5.9 and SQLite 3.51.3 environment passed actual Ubuntu 26.04.1 ARM64 acceptance; the separate Ubuntu 24.04 recipe is not an executed acceptance claim. Operating-system and bootstrap-tool maintenance remains the operator's responsibility.
- Authenticated control operations pause if UTC moves backward below the durably recorded authentication time. They resume when that time is reached. This preserves replay protection after nonce pruning and restart; operators must maintain reliable system time and follow the documented backup/secret-rotation procedure.
